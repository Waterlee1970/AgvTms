## 四、差距分析与根因

### 4.1 P0 差距：大规模集群调度（最大瓶颈）

| 指标 | AGV-TMS | 海康 RCS-2000 | 倍数差距 |
|------|---------|--------------|---------|
| 最大 AGV 调度数 | ~50（仿真验证） | 2000+ | **40x** |
| 最大任务并发 | ~150 仿真步 | 1 秒内 1000 台×2000 任务匹配 | **~100x** |
| 架构模式 | 单机 FastAPI | 分布式微服务 | 根本性差异 |
| 数据管道 | 同步 DB+Redis | Kafka+Flink 流处理 | 根本性差异 |

**根因**: 单体 FastAPI + 同步 ThreadPoolExecutor 架构无法横向扩展，缺乏分布式协调（如 etcd/ZooKeeper）和消息队列解耦。

### 4.2 P1 差距：工业协议栈不完整

- **缺失 MQTT 消息总线** — Phase 1 标记为待实施，海康/仙工均已标配
- **缺失 Modbus TCP** — PLC 对接刚需，海康标配
- **VDA5050 深度不足** — 当前仅 6 个基础端点，缺乏完整的 order/edge/node/instantAction JSON 消息体实现

### 4.3 P1 差距：高可用与容灾

- **无主备热切换** — 单实例宕机即全系统不可用
- **无数据同步机制** — Redis 缓存丢失后无法从 DB 快速重建
- **无灰度发布** — 算法切换无 A/B 测试能力

### 4.4 P2 差距：可视化与数字孪生

- **当前**: Canvas 2D 实时动画 + 雷达图对比（已达良好水平）
- **行业前沿**: 3D 数字孪生 + 热力图 + 历史回放系统
- **差距**: 中等，非核心瓶颈

## 五、发展路径规划（v1.7 ~ v2.0）

### Phase 2: 规模化与高可用（v1.7，预计 4-6 周）

#### P0-2.1 分布式架构改造
```
当前: FastAPI(单机) → ThreadPoolExecutor → DB
目标: API Gateway → [Scheduler Service ×N] → Kafka → Flink → DB+InfluxDB
```
- 引入 Kafka 消息队列解耦调度引擎
- 调度服务无状态化，支持 K8s 水平扩展
- 引入 etcd 做分布式锁和领导者选举

#### P0-2.2 MQTT 消息总线实施
- 补齐 Phase 1 遗留的 P0-1.5
- MQTT 主题设计: `agv/{id}/status`, `agv/{id}/command`, `system/alert`
- 与 OPC UA 形成「南向双协议」覆盖

#### P0-2.3 时序数据库引入
- 新增 InfluxDB 存储AGV轨迹、电量、速度时序数据
- 历史回放功能依赖时序数据

#### P1-2.4 高可用方案
- FastAPI 主备部署 + Keepalived VIP
- Redis Sentinel 哨兵模式
- PostgreSQL 流复制

### Phase 3: 协议深化与生态（v1.8，预计 4 周）

#### P0-3.1 VDA5050 完整实现
- 完整的 order/edge/node/instantAction JSON Schema
- AGV 状态上报的 14 个标准字段
- 与仙工星云平台的互操作性测试

#### P0-3.2 Modbus TCP 协议适配
- PLC 设备对接（输送线/提升机/充电桩）
- 寄存器映射配置化

#### P1-3.3 跨品牌混合调度
- 基于 VDA5050 实现异构 AGV 统一调度
- 地图坐标转换层（不同品牌坐标系对齐）

### Phase 4: 智能化与数字孪生（v2.0，预计 6-8 周）

#### P0-4.1 3D 数字孪生
- Three.js / Babylon.js 重构前端可视化
- 实时 AGV 3D 模型 + 路径轨迹 + 热力图

#### P0-4.2 RL 调度生产化
- DQN/PPO 模型在线训练 + 推理服务
- A/B 测试框架（RL vs MIP 对比）

#### P1-4.3 自适应调度
- 神经网络评估 AGV-任务匹配（参考 2025 学术研究）
- 动态权重调整：距离/等待时间/缓冲区/电量
