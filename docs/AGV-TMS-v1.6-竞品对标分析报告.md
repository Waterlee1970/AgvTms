> **版本**: v1.6 (1.5 分支演进)

> **目的**: 明确差距、制定优化路线图

## 一、执行摘要

### 1.1 核心结论

| 维度 | 当前状态 (AGV-TMS) | 行业头部 (海康/极智嘉) | 差距等级 |
|------|---------------------|------------------------|----------|
| **算法完备性** | ★★★★☆ 6种算法，含 MIP+RL+预测引擎 | ★★★★★ MAPF 全向路径规划 + 自学习调度 | **中** |
| **架构成熟度** | ★★☆☆☆ 单体 FastAPI + 同步阻塞 | ★★★★★ 分布式微服务 + Kafka+Flink 流处理 | **大** |
| **规模能力** | ★★☆☆☆ ~50AGV, 150仿真步, 单机部署 | ★★★★★ 1000+ AGV 集群, 区域分布式控制 | **大** |
| **工程化水平** | ★★★☆☆ Docker Compose, 基础 CI | ★★★★★ K8s 编排, 高可用, 多租户 | **大** |
| **可视化体验** | ★★★★☆ Canvas 实时动画 + 雷达图对比 | ★★★★★ 3D 数字孪生 + 热力图 + 回放系统 | **小** |
| **协议兼容性** | ★☆☆☆☆ 仅 REST API | ★★★★★ OPC UA / MQTT / Modbus / VDA 5050 | **极大** |
| **场景覆盖** | ★★★★☆ 纯AGV + 输送线混合 + 故障注入 | ★★★★★ 全场景(仓储/产线/港口/医院) + 多车型混行 | **小** |

### 1.2 一句话总结

**AGV-TMS 在算法研究层面已达到行业先进水平（6 种算法 + 三层编排 + RL + 预测），但在系统工程化、大规模集群调度、工业协议对接方面与海康 RCS-2000 等商业产品存在显著差距。核心短板在于「算法强但工程弱」，需在 1.6 版本重点补齐架构升级和工业适配。**

## 二、主流竞品深度解析

### 2.1 海康机器人 RCS-2000 V4.0 / RCS-Lite

#### 产品定位
- **RCS-2000**: 大规模工业级调度控制器（旗舰版）
- **RCS-Lite**: 轻量级中小型 AMR 项目（2024 新推出）

#### 核心技术参数

| 能力维度 | RCS-2000 指标 | RCS-Lite 指标 |
|----------|---------------|---------------|
| **最大调度规模** | **1000+ 台**机器人集群 | ~100 台 |
| **支持车型** | 潜伏式 / 叉车 / CTU / 移动复合 / 线边搬运全系列 | 潜伏 / 叉车 / 单箱CTU |
| **导航方式** | 二维码 / SLAM / 纹理 / GPS / 激光融合 | 二维码 / SLAM / 纹理 |
| **路径规划** | 改进 A* (十六邻域) + TW-A* (时间窗) + 死锁检测(Wait-for Graph) | 增量式 A* + 区域交通管制 |
| **任务分配** | 多目标优化(时间/能耗/均衡)+ 动态插队 | 规则优先级 + 最近分配 |
| **通信协议** | **OPC UA / MQTT / Modbus TCP / WebSocket / HTTP** | REST + WebSocket |
| **系统集成** | WMS/MES/ERP 标准接口 + 自定义流程编排引擎 | REST API + 简单 Web UI |
| **数据存储** | MySQL + Redis + InfluxDB 时序数据库 | 内置 SQLite / 可选 PostgreSQL |
| **高可用** | 主备热切换 + 数据同步 | 单实例 |

#### 架构分层（四层）

```
┌─────────────────────────────────────────────┐
│  接入交互层: WMS/MES/ERP 对接 + HMI + 边缘设备接入 │
├─────────────────────────────────────────────┤
│  核心业务层: 任务管理引擎 + 智能调度引擎 + 资源锁控 │
├─────────────────────────────────────────────┤
│  数据服务层: MySQL + Redis + InfluxDB + Kafka   │
├─────────────────────────────────────────────┤
│  底座基础层: OPC UA 协议栈 + Modbus + 硬件网关    │
└─────────────────────────────────────────────┘
```

#### 关键差异化功能
1. **流程编排引擎** — 用户可自由搭配业务流程节点
2. **多车型混行调度** — 不同导航方式的 AGV 共用同一地图
3. **死锁检测与解除** — Wait-for Graph 分析 + 资源剥夺法
4. **区域交通管制** — 路口优先级规则 + 时空窗预约

## 四、差距根因分析

### 4.1 架构层面的根本问题

```
问题 1: 单体同步阻塞架构
┌──────────────────────────────────────────┐
│  Client → [FastAPI] → algorithm.execute() │
│                     ↑                     │
│          阻塞 N 秒 (6个算法顺序执行)        │
│          事件循环被占用, 无法服务其他请求    │
└──────────────────────────────────────────┘
影响: 无法支撑并发调度请求, 单点瓶颈

解决方案: 
  - 短期: Celery/RQ 异步任务队列
  - 中期: Actor 模型 (Ray/Dask) 并行计算
  - 长期: 微服务拆分 (调度引擎独立部署)

问题 2: 无分布式协调机制
当前: 内存字典 + 文件 JSON 存储状态
影响: 单机上限 ~50 AGV, 无法横向扩展

解决方案:
  - Redis Cluster 共享状态
  - 分区调度 (按地图区域分片)

问题 3: 无工业协议栈
当前: 仅 HTTP REST
影响: 无法对接真实 AGV 设备、充电桩、电梯、门禁

解决方案:
  - 集成 asyncua (OPC UA)
  - 集成 paho-mqtt (MQTT)
  - 实现 VDA 5050 接口适配器
```

### 4.2 算法层面的不足

| 问题 | 影响 | 优先级 |
|------|------|--------|
| 无死锁检测 (Wait-for Graph) | 高密度场景下 AGV 可能陷入循环等待 | P0 |
| 无任务插队/抢占机制 | 紧急订单无法优先处理 | P0 |
| 无全向路径规划 (Omni-MAPF) | 不支持全向移动的 AMR 机器人 | P1 |
| 无 CBS (Conflict-Based Search) | 多机路径冲突解决不够最优 | P1 |
| MIP 求解超时无降级策略 | 大规模场景可能超时卡死 | P1 |
| RL 模型需要预训练 | 冷启动时退化为贪心, 无在线学习能力 | P2 |

## 八、总结与建议

### 核心观点

1. **算法层面已经具备竞争力** — 6 种算法 + 三层编排 + RL + 预测的组合在学术/研究层面已达到较高水准，特别是评测框架和算法对比能力是差异化亮点

2. **工程化是最大短板** — 从"能跑通 demo"到"工业可用"之间隔着异步化、协议适配、状态持久化、监控告警等大量工程工作

3. **建议聚焦 v1.6 的 5 个关键突破点**：
   - **异步调度引擎** (解放并发)
   - **死锁检测** (保障安全性)
   - **OPC UA 适配** (打通真实设备)
   - **Redis 状态中心** (支撑规模化)
   - **WMS/MES 接口** (融入生态)

4. **不要试图一步到位** — v1.6 定位为"可演示的工业原型", v2.0 再追求"商业化产品"。每个版本都要有可运行的交付物。
